# 《杀戮尖塔 2》代码架构与卡牌设计研究

> 当前项目规则更新（2026-09-30）：本文提及的“补到 5 张、上限 10 张”是历史版本。当前可选择沈明（旧牌保留、首回合抽 5 张、后续每回合新增 3 张、可主动弃最多 2 张）或宋梅（每回合弃旧牌并抽 5 张）。两人共用 12 张基础起始牌，回合中可暂时超过 8 张，只在结束回合时须整理到 8 张或以下。地图现按种子生成分叉路径，并有商店与带代价的事件。见 [第一章路线与卡牌数值 v0.2](第一章路线与卡牌数值-v0.2-2026-09-30.md)。

> 研究日期：2026-09-30。用途：为《阿卡姆号》的战斗、卡牌构筑和后续爬塔设计提供机制参考。本文记录结构和设计方法，不收录反编译源码、完整卡牌文本或美术资源。

## 0. 证据边界与来源

《杀戮尖塔 2》并未在本文所用资料中以官方开源项目的形式发布。公开的 [Spire Codex](https://github.com/ptrlrd/spire-codex) 是第三方数据研究项目：其 [README](https://github.com/ptrlrd/spire-codex#how-it-works) 说明游戏使用 Godot 4，主要游戏逻辑位于 C#/.NET 8 的 `sts2.dll`；该项目以 GDRE Tools 处理资源包、以 ILSpy 处理 DLL，再由解析器生成结构化数据。它的 [更新脚本](https://github.com/ptrlrd/spire-codex/blob/main/tools/update.py) 可以核对这一流水线。[卡牌解析器](https://github.com/ptrlrd/spire-codex/blob/main/backend/app/parsers/card_parser.py) 可核对卡牌构造参数与升级字段提取方式。

本项目已有的 [《尖塔2-卡牌交互与判定-逆向笔记》](尖塔2-卡牌交互与判定-逆向笔记.md) 记录了另一次基于 Android 包内 `sts2.dll` 的 ILSpy 观察。该文件是项目内笔记，包含具体类名和时序，但目前缺少可重复下载的 DLL 版本与逐项反编译定位，因此本文把它标为 **本地逆向笔记**，不把每个常量当成跨版本不变的官方规范。

本文的数据统计来自 Spire Codex 的 [英语卡牌 JSON](https://github.com/ptrlrd/spire-codex/blob/main/data/eng/cards.json)。该文件查询时为 577 条，最近一次相关提交时间为 2026-07-15；数据是解析器输出，可能因游戏版本、单人/联机筛选、解析准确率而变化。**下文的统计是这份快照的统计，不等于官方公布的卡牌总数。**

### 使用边界

Spire Codex 的 [许可说明](https://github.com/ptrlrd/spire-codex#license) 将其源代码置于 PolyForm Noncommercial 许可下，游戏数据归 Mega Crit。因而本项目应研究抽象机制、重新实现自己的代码与卡牌内容，不直接复制第三方仓库源码、大量卡牌文本、图像或音效。用户所说的“模仿”在这里落实为可验证的交互与系统设计。

## 1. 从资料中能确认的整体结构

### 1.1 技术和资源边界

- **引擎层**：Godot 4 负责节点、场景、输入、动画和渲染。游戏逻辑主要是 C#/.NET 8；不能因为使用 Godot 就假定其核心代码是 GDScript。[来源：Spire Codex README](https://github.com/ptrlrd/spire-codex#how-it-works)
- **资源层**：资源包包含图片、动画及本地化文本；DLL 与资源包分工。解析出的 JSON 是研究项目为检索生成的中间数据，**不是游戏直接读取的原生卡牌配置格式**。[来源：更新脚本](https://github.com/ptrlrd/spire-codex/blob/main/tools/update.py)
- **模型层**：公开解析器从卡牌 C# 类的基类构造中读取费用、类型、稀有度和目标类型，并扫描 `DamageVar`、`BlockVar`、`PowerVar<T>` 一类数值以及升级行为。可见其卡牌至少由静态身份、可变数值与行为钩子共同构成，而非只有一句效果文本。[来源：卡牌解析器](https://github.com/ptrlrd/spire-codex/blob/main/backend/app/parsers/card_parser.py)
- **运行层**：本地逆向笔记记录了 `CardModel.CanPlay`、`NMouseCardPlay`、`NTargetManager`、`NCardPlayQueue`、`RunManager.ActionQueueSet` 等名称。由这些名称和时序可推断：输入选择、合法性判定、行动结算、视觉队列是分开的职责。具体类图并未完整验证。[来源：本地逆向笔记](尖塔2-卡牌交互与判定-逆向笔记.md)

```mermaid
flowchart LR
  I[鼠标/手柄输入] --> U[卡牌交互与目标选择]
  U --> V[出牌合法性检查]
  V --> Q[行动队列]
  Q --> M[战斗模型/效果结算]
  M --> E[事件与状态变更]
  E --> P[卡牌、角色、数值表现]
  D[卡牌定义与升级数据] --> V
  D --> M
```

这张图是**用于本项目的架构归纳**，不是《杀戮尖塔 2》完整官方 UML。它最重要的约束是：视觉动画不可成为战斗数值的唯一来源；一张牌能不能打、对谁生效和怎样表现应分别处理。

### 1.2 内容目录反映出的数据域

Spire Codex 的 [数据目录](https://github.com/ptrlrd/spire-codex/tree/main/data/eng) 分别整理卡牌、角色、遗物、药水、敌人、遭遇、事件、能力/状态、章节等。其 [角色数据](https://github.com/ptrlrd/spire-codex/blob/main/data/eng/characters.json) 至少有初始生命、金币、能量、起始牌组、初始遗物等字段。这说明爬塔内容需要一层“运行中的牌组/资源/路线状态”，不能把所有状态塞进单场战斗 UI。该目录是第三方整理结果，不证明游戏内部恰好采用同样的文件目录。

## 2. 卡牌设计：从数据结构看可复用的规律

### 2.1 一张卡的最小信息集合

公开 [卡牌 JSON](https://github.com/ptrlrd/spire-codex/blob/main/data/eng/cards.json) 每条记录通常可见：`id/name`、描述与原始模板、`cost`、`type`、`rarity`、`target`、所属颜色、伤害/格挡/抽牌/能量/状态等解析字段、关键词、生成牌、升级变化、图像路径和图鉴顺序。有些字段为空，并非每张牌都同时拥有这些能力。

卡牌设计不能只填写“费用 + 描述 + 伤害”。至少要回答：

1. **何时可用**：费用、不能打出的状态、目标是否存在、当前回合限制。
2. **选择什么**：自身、单敌、全敌、随机敌、友方或无目标。
3. **支付什么**：能量、生命、资源或额外风险。
4. **按什么顺序结算**：抽牌、伤害、格挡、施加状态、生成牌、连锁触发的次序。
5. **结算后去哪里**：弃牌、消耗、回手、留牌或其他特殊牌区。
6. **升级改什么**：伤害、格挡、费用、关键词、目标、附加行为，而不必永远是 `+2` 数值。
7. **怎样提示玩家**：动态数值、费用变化、目标高亮、无法打出的原因。

卡牌数据快照中的字段是解析结果，复杂卡牌未必可用扁平字段完整表达；研究自己的卡牌时不能把 JSON 里的 `damage: null` 简单解读为“绝不会造成伤害”。

### 2.2 类型、目标和升级的规模感

577 条快照中：Skill 234、Attack 195、Power 111、Curse 18、Status 16、Quest 3；目标为 Self 303、AnyEnemy 183、AllEnemies 35、None 34、RandomEnemy 9、AnyAlly 8、AllAllies 5。费用 1 的记录为 293，费用 0 为 114，费用 2 为 94。`upgrade` 非空的记录为 541。以上均是第三方解析器截至上述快照的分类统计，不可直接当成我们卡池应复制的比例。[数据来源](https://github.com/ptrlrd/spire-codex/blob/main/data/eng/cards.json)

可借鉴的不是这些比例本身，而是几个设计事实：

- **目标类型是一等数据**：UI 的拖拽、箭头和取消规则必须依目标类别变，而不能由“攻击/技能”的卡面类型猜测。
- **费用分布以 1 费为主体**，0/2/3 费制造节奏差异。具体平衡必须用本游戏的能量、留牌和抽牌规则重算。
- **升级覆盖面很广**，并不意味着每张升级都只加数值。解析器还识别费用升级、关键词变化和变量升级。[来源：卡牌解析器](https://github.com/ptrlrd/spire-codex/blob/main/backend/app/parsers/card_parser.py)
- **特殊牌是系统的一部分**：诅咒、状态、任务牌等会占据抽牌/手牌资源，具有与普通可打牌不同的合法性和去向。

### 2.3 关键词和组合系统

快照中能检出的关键词包括 Exhaust 99、Unplayable 26、Ethereal 18、Retain 11、Innate 9、Sly 8、Eternal 7；这些数字只代表解析器产生的记录数。还有 81 条带抽牌解析字段、43 条带能量获取字段、38 条带生成牌字段。由此可见，卡牌价值相当一部分来自**对牌流和回合资源的改写**，而非纯伤害。[数据来源](https://github.com/ptrlrd/spire-codex/blob/main/data/eng/cards.json)

对《拉莱耶之门》特别重要的区别：尖塔式 **Retain** 是个别牌的关键词；本项目把全手牌保留设为沈明的角色规则，首回合抽 5 张、后续每回合新增 3 张。宋梅仍采用回合结束弃旧牌、下回合抽 5 张的常规轮转。沈明规则会显著抬高定向找牌、手牌规划、0 费牌和抽牌牌的价值，后续设计必须按角色分别测算，不能照搬尖塔卡牌数值。

### 2.4 推荐的原创卡牌设计流程

每张原创卡先写一行战术职责，再写数值。例如“用隔离风险换取快速过牌”“积累规程牌以获得稳定格挡”“迫使玩家在留牌与当前防御之间取舍”。接着写触发条件、费用与目标、结算顺序、离开手牌的去向、升级分支、UI 提示和反例测试。这样容易发现重复功能，也能避免描述与实际逻辑分叉。

## 3. 战斗代码与交互时序

以下具体实现观察主要来自 [本地逆向笔记](尖塔2-卡牌交互与判定-逆向笔记.md)，属于 B 级证据；方案部分属于 C 级推论。

### 3.1 从拿起牌到生效

笔记中的 `NMouseCardPlay` 有出牌区、取消区、拖拽起点相关阈值和不同目标模式。一次出牌大致经过：拿起/拖动 → 进入出牌候选区 → `CanPlay` 检查 → 开始目标选择 → 松手时再次验证 → 交给行动队列。失败、取消和输入设备切换都要清理目标提示。**验证两次**能避免开始拖动时合法、松手时目标或费用已变化的错配。

本项目的用户要求是：瞄准时卡牌仍留在底部，拖动的是箭头；点击牌则在中间平滑放大阅读。因此应该借鉴判定边界与取消逻辑，但不要照搬笔记里原游戏的卡牌 holder 跟随鼠标行为。交互状态建议明确为 `idle / preview / targeting / queued / resolving / cancelled`，并让每一态统一拥有鼠标与 UI 的清理入口。

### 3.2 牌的“能打”与“怎么打”分离

笔记中的 `CardModel.CanPlay` 考虑费用、卡牌禁用位、目标和额外规则，并有不同的高亮/不可用提示。对应本项目至少要分：

- **纯逻辑判定**：当前阶段、手牌归属、费用、目标、隔离阈值、状态限制。
- **原因列表**：不足费用、无可用目标、特殊状态禁止等；UI 只读取结果。
- **视觉映射**：可打高亮、不可打弱化、有效目标准星、错误提示。

避免在一个 `_on_card_released()` 里同时修改能量、找敌人、播放动画和删除手牌；否则取消、重启以及连续打牌时会难以保证一致。

### 3.3 行动队列和数值时点

笔记中的 `NCardPlayQueue` 监听行动入队事件，将卡牌交给队列视觉，依序播放；数值状态可晚于输入时更新。我们不必复制其类结构，但应规定：**一次出牌仅提交一次**，提交后锁定输入，逻辑效果依序结算，视觉效果订阅结算事件，完毕后释放锁定。快速连续点击、目标死亡、战斗提前结束、重开都需要让队列中未完成的视觉动作可取消。

应为关键事件定义稳定顺序，例如：

`尝试出牌 → 校验目标与费用 → 支付费用 → 卡牌离手 → 连击/隔离变化 → 卡牌效果 → 弃牌或消耗 → 胜负检查 → 对应表现收尾`。

这只是《阿卡姆号》的推荐契约，不能声称是尖塔 2 的完整内部结算顺序。尤其是本项目已有“回声先于本牌效果结算”的设计，应保留并通过测试固定。

### 3.4 表现与逻辑使用同一份效果事实

本项目目前要求攻击牌飞向敌人，辅助牌呈蓝色粒子消散。视觉分类应来自卡牌**实际效果与有效目标**：带 `damage` / `damage_multi` 的牌走攻击表现；只有格挡、抽牌、能量、隔离变化等效果的牌走辅助表现。若卡牌混合多种效果，先以最有辨识度的主要效果定牌的去向，再按各个效果事件播放命中、数值和状态反馈。不能只凭卡面 `type` 判定，因为“技能牌伤害”“攻击牌自带格挡”等组合可能出现。

### 3.5 手牌布局与抽牌动画

笔记中的 `NHandCardHolder` 将位置、旋转、缩放分别平滑插值，`HandPosHelper` 按手牌数提供布局。可以借鉴“位置可随时改变、过渡可打断”的原则。当前项目的手牌保留规则还要求：

- 回合结束时现有牌保持原 `CardInstance` 身份及顺序，不播放整手弃牌效果；
- 回合开始只对**新进入手牌**的牌播放从牌库逐张发牌；
- 沈明后续回合固定新增 3 张，宋梅重新抽 5 张；卡牌效果可额外抽牌。回合中允许超过 8 张，结束回合时展示全部候选牌并由玩家选弃到 8 张或以下；
- 抽牌堆耗尽才将弃牌堆洗回抽牌堆，不能把手中牌洗入。

## 5. 爬塔路径：本轮只做设计，不实现

用户当前优先级是战斗手感。后续路径系统宜先确定一条“有选择、能预判、可回看”的最小闭环：

1. 地图由若干层节点构成，当前节点只连接下一层若干可达节点；每层明确节点类型，例如普通战、精英、休整、事件、商店、首领。
2. 路线选择的核心信息是风险与回报：可预见的节点类型、剩余生命与牌组短板、可能获得的卡牌/资源，而非纯随机按钮。
3. 在非肉鸽爬塔目标下，**固定章节骨架 + 可变化的支路事件/遭遇**比全局随机地图更容易承载个人 RPG 剧情。固定剧情节点不强迫每条支线同样展开。
4. 路径存档独立于单场战斗：记录章节、节点、已访问分支、牌组、生命、资源、剧情标志。战斗奖励先作用于运行状态，再进入下一节点。
5. 先做纸面节点图和两条有真实取舍的分支；验证玩家是否能说清“为什么走这条路”，再扩节点数量。

这里借鉴的是卡牌爬塔的选择结构，路线生成算法并未从目前资料里核实，故不声称尖塔 2 使用上述具体实现。

**当前战斗版本**：沈明保留未打出的手牌并在后续回合新增 3 张，宋梅每回合重新抽 5 张；维持逐张抽牌动画；回合中可超过 8 张，结束回合时由玩家选择弃至 8 张；确保回合抽牌、卡牌额外抽牌、洗牌和消耗互不混淆。
